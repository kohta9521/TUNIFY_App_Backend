# TUNIFY Backend プロジェクト構造完全解説

このドキュメントは、Rust 初心者向けにプロジェクト全体の構造、ファイル命名規則、コードの意味を詳しく解説します。

## 📁 プロジェクト構造（全体像）

```
tunify-backend/
├── Cargo.toml          # プロジェクト設定ファイル
├── Cargo.lock          # 依存関係のロックファイル（自動生成）
├── Dockerfile          # Dockerイメージの定義
├── src/                # ソースコードディレクトリ
│   ├── main.rs         # エントリーポイント（プログラムの開始点）
│   ├── domains/        # ドメイン層（ビジネスロジックの核心）

│   ├── application/    # アプリケーション層（ユースケース）
│   │   ├── mod.rs      # モジュール宣言
│   │   ├── status_service.rs   # ステータスサービスの実装
│   │   └── health_service.rs    # ヘルスチェックサービスの実装
│   └── presentation/   # プレゼンテーション層（HTTP API）

└── target/             # ビルド成果物（自動生成、gitignore対象）
```

## 🏗️ アーキテクチャパターン：クリーンアーキテクチャ

このプロジェクトは**クリーンアーキテクチャ**という設計パターンを使っています。

### 3 つの層の役割

```
┌─────────────────────────────────────┐
│   Presentation Layer (プレゼン層)   │  ← HTTPリクエストを受け取る
│   - routes.rs                       │
│   - handlers/                       │
└──────────────┬──────────────────────┘
               │ 呼び出す
               ▼
┌─────────────────────────────────────┐
│  Application Layer (アプリ層)        │  ← ビジネスロジックを実行
│  - status_service.rs                │
│  - health_service.rs                 │
└──────────────┬──────────────────────┘
               │ 使用する
               ▼
┌─────────────────────────────────────┐
│   Domain Layer (ドメイン層)          │  ← データ構造を定義
│   - status.rs                       │
└─────────────────────────────────────┘
```

**なぜこの構造？**

- **関心の分離**: 各層が独立しているので、変更が他の層に影響しにくい
- **テストしやすい**: 各層を個別にテストできる
- **保守しやすい**: どこに何があるかが明確

## 📝 ファイル命名規則

### Rust の命名規則

1. **ファイル名**: `snake_case`（小文字 + アンダースコア）

   - ✅ `status_service.rs`
   - ✅ `health_check.rs`
   - ❌ `StatusService.rs`（大文字は使わない）

2. **モジュールファイル**: `mod.rs`

   - ディレクトリをモジュールとして使う時に必要
   - 例: `application/mod.rs` → `application`モジュール

3. **構造体・関数名**: `PascalCase`（大文字始まり）

   - ✅ `StatusService`
   - ✅ `ApiStatus`
   - ✅ `create_router()`

4. **変数名**: `snake_case`（小文字 + アンダースコア）
   - ✅ `let app = ...`
   - ✅ `let listener = ...`

### 2. `src/main.rs` - エントリーポイント

**役割**: プログラムの開始点。最初に実行されるファイル。

#### コード解説

```rust
// 1-3行目: モジュール宣言
mod application;    // applicationディレクトリをモジュールとして使う
mod domains;        // domainsディレクトリをモジュールとして使う
mod presentation;   // presentationディレクトリをモジュールとして使う
```

**`mod`とは？**

- Rust でモジュール（ファイルやディレクトリ）を使う時に宣言する
- 他のファイルのコードを使えるようにする

```rust
// 5-7行目: 外部ライブラリのインポート
use axum::Router;           // Webルーター
use tokio::net::TcpListener; // TCP接続を受け付ける
use tracing_subscriber::...;  // ログ設定
```

**`use`とは？**

- 他のモジュールやライブラリから機能を使えるようにする
- `use std::collections::HashMap;` → `HashMap`を直接使える

```rust
// 9行目: 自分のプロジェクト内のモジュールを使う
use crate::presentation::routes::create_router;
```

**`crate`とは？**

- 現在のプロジェクト（パッケージ）を指す
- `crate::presentation::routes` → `src/presentation/routes.rs`

```rust
// 11行目: 非同期ランタイムの設定
#[tokio::main]
async fn main() -> anyhow::Result<()> {
```

**解説**:

- `#[tokio::main]`: Tokio という非同期ランタイムを使うマクロ
- `async fn`: 非同期関数（`await`が使える）
- `-> anyhow::Result<()>`: エラーが発生する可能性があることを示す
  - `Ok(())`: 成功
  - `Err(...)`: エラー

```rust
// 13行目: ログの初期化
init_tracing();
```

**`init_tracing()`関数**:

- ログ出力の設定を行う
- `RUST_LOG`環境変数でログレベルを変更できる

```rust
// 15行目: ルーターを作成
let app: Router = create_router();
```

**解説**:

- `let`: 変数を宣言
- `app`: 変数名
- `: Router`: 型を明示（省略可能）
- `create_router()`: ルーティングを設定する関数

```rust
// 17行目: サーバーのアドレス
let addr = "0.0.0.0:8085";
```

**解説**:

- `0.0.0.0`: すべてのネットワークインターフェースで待ち受け
- `:8085`: ポート番号 8085

```rust
// 24行目: TCPリスナーを作成
let listener = TcpListener::bind(addr).await?;
```

**解説**:

- `TcpListener::bind()`: 指定したアドレスで待ち受けを開始
- `.await`: 非同期処理の完了を待つ
- `?`: エラーが発生したら関数を終了（`Result`型のショートカット）

```rust
// 27行目: サーバーを起動
axum::serve(listener, app).await?;
```

**解説**:

- `axum::serve()`: Axum サーバーを起動
- この行でサーバーが動き続ける（無限ループ）

### 3. `src/domains/` - ドメイン層

**役割**: ビジネスロジックの核心となるデータ構造を定義

#### `domains/mod.rs`

```rust
pub mod status;  // status.rsを公開モジュールとして宣言
```

**解説**:

- `pub`: 他のモジュールから使えるようにする（公開）
- `mod status`: `status.rs`ファイルをモジュールとして使う

#### `domains/status.rs`

```rust
#[derive(Debug, Clone)]
pub struct ApiStatus {
    pub message: String,
}
```

**解説**:

- `#[derive(Debug, Clone)]`: 自動的に`Debug`と`Clone`トレイトを実装
  - `Debug`: `println!("{:?}", status)`で表示できる
  - `Clone`: `.clone()`でコピーできる
- `pub struct`: 公開構造体（他のモジュールから使える）
- `pub message`: 公開フィールド（外部からアクセス可能）

**なぜドメイン層？**

- ビジネスロジックの核心となるデータ構造
- HTTP やデータベースに依存しない純粋なデータ

### 4. `src/application/` - アプリケーション層

**役割**: ビジネスロジックを実装（ユースケース）

#### `application/mod.rs`

```rust
pub mod health_service;   // health_service.rsを公開
pub mod status_service;   // status_service.rsを公開
```

#### `application/status_service.rs`

```rust
// 1行目: ドメイン層の型を使う
use crate::domains::status::ApiStatus;

// 3行目: サービス構造体を定義
pub struct StatusService;

// 5-8行目: インスタンスを作成する関数
impl StatusService {
    pub fn new() -> Self {
        Self  // StatusServiceのインスタンスを返す
    }
```

**解説**:

- `impl`: 構造体にメソッドを実装する
- `Self`: 現在の型（この場合は`StatusService`）
- `new()`: コンストラクタ（インスタンスを作る関数）

```rust
// 10-14行目: ステータスを取得するメソッド
pub fn get_status(&self) -> ApiStatus {
    ApiStatus {
        message: "API is running".to_string(),
    }
}
```

**解説**:

- `&self`: 自分自身への参照（メソッドを呼ぶ時に必要）
- `-> ApiStatus`: 戻り値の型
- `.to_string()`: 文字列リテラル（`"..."`）を`String`型に変換

**なぜアプリケーション層？**

- ビジネスロジックを実装する場所
- ドメイン層のデータを使って処理を行う

### 5. `src/presentation/` - プレゼンテーション層

**役割**: HTTP リクエストを受け取り、レスポンスを返す

#### `presentation/routes.rs`

```rust
// 1行目: Axumの機能を使う
use axum::{routing::get, Router};

// 4行目: ハンドラー関数を使う
use crate::presentation::handlers::{health::health_check, status::api_status};

// 6行目: ルーターを作成する関数
pub fn create_router() -> Router {
    Router::new()                    // 新しいルーターを作成
        .route("/api/v1/status", get(api_status))    // GET /api/v1/status
        .route("/api/v1/health", get(health_check))   // GET /api/v1/health
        .layer(...)                  // ミドルウェア（ログなど）を追加
}
```

**解説**:

- `.route()`: URL パスとハンドラー関数を紐付ける
- `get()`: HTTP GET メソッドを指定
- `.layer()`: ミドルウェアを追加（リクエストログなど）

#### `presentation/handlers/status.rs`

```rust
// 1-2行目: 必要な型をインポート
use axum::response::Json;  // JSONレスポンス
use serde::Serialize;      // シリアライゼーション（JSON変換）

// 4-5行目: 他の層のコードを使う
use crate::application::status_service::StatusService;
use crate::domains::status::ApiStatus;

// 7-10行目: レスポンス用の構造体
#[derive(Serialize)]
pub struct StatusResponse {
    message: String,
}

// 12-19行目: ハンドラー関数
pub async fn api_status() -> Json<StatusResponse> {
    tracing::debug!("Handling /api/v1/status request");

    let service = StatusService::new();           // サービスを作成
    let ApiStatus { message } = service.get_status();  // ステータスを取得

    tracing::debug!("Status response: {}", message);
    Json(StatusResponse { message })             // JSONレスポンスを返す
}
```

**解説**:

- `pub async fn`: 公開非同期関数
- `-> Json<StatusResponse>`: JSON 形式で`StatusResponse`を返す
- `let ApiStatus { message } = ...`: 構造体から`message`フィールドを取り出す（分割代入）

**なぜプレゼンテーション層？**

- HTTP リクエストを受け取る場所
- アプリケーション層を呼び出して、結果を HTTP レスポンスに変換

## 🔄 データの流れ（リクエスト処理の流れ）

### 例: `/api/v1/status`にアクセスした時

```
1. HTTPリクエスト
   ↓
2. routes.rs: ルーティング設定で`api_status`ハンドラーを呼び出し
   ↓
3. handlers/status.rs: `api_status()`関数が実行
   ↓
4. application/status_service.rs: `StatusService::get_status()`を呼び出し
   ↓
5. domains/status.rs: `ApiStatus`構造体を返す
   ↓
6. handlers/status.rs: `StatusResponse`に変換してJSONで返す
   ↓
7. HTTPレスポンス: {"message": "API is running"}
```

## 📚 重要な Rust の概念

### 1. モジュールシステム

```rust
// モジュールを宣言
mod application;

// モジュールを使う
use crate::application::status_service::StatusService;
```

**階層構造**:

```
crate (プロジェクト全体)
  └── application (モジュール)
      └── status_service (モジュール)
          └── StatusService (構造体)
```

### 2. 所有権（Ownership）

```rust
let service = StatusService::new();  // serviceが所有権を持つ
let status = service.get_status();   // statusが所有権を持つ
```

**重要なルール**:

- 1 つの値に対して、1 つの所有者しか存在しない
- 所有権を移動すると、元の変数は使えなくなる

### 3. 参照（Reference）

```rust
pub fn get_status(&self) -> ApiStatus {
    // &self: 自分自身への参照（所有権を移動しない）
}
```

**`&`の意味**:

- 参照を借りる（借用）
- 所有権を移動せずに値を使える

### 4. エラーハンドリング

```rust
async fn main() -> anyhow::Result<()> {
    let listener = TcpListener::bind(addr).await?;  // ?でエラーを伝播
    Ok(())  // 成功を返す
}
```

**`Result<T, E>`型**:

- `Ok(value)`: 成功
- `Err(error)`: エラー
- `?`: エラーが発生したら関数を終了

## 🎯 まとめ

### ファイル命名規則

- ファイル名: `snake_case`（小文字 + アンダースコア）
- 構造体名: `PascalCase`（大文字始まり）
- 関数名・変数名: `snake_case`

### 3 層アーキテクチャ

1. **Domain 層**: データ構造を定義
2. **Application 層**: ビジネスロジックを実装
3. **Presentation 層**: HTTP リクエストを処理

### コードの流れ

```
HTTPリクエスト
  → routes.rs (ルーティング)
  → handlers/*.rs (ハンドラー)
  → application/*.rs (サービス)
  → domains/*.rs (データ構造)
  → HTTPレスポンス
```
